# 企画 — 問いの棚「今日の問い」（呼び戻し × プッシュ）

最終更新: **2026-07-16**  
ステータス: **企画（実装前）**  
前身: [design-scheduled-recall-question.md](./design-scheduled-recall-question.md)（ホーム先頭案）→ **本企画で置き場を問いの棚に再定義**

---

## 1. 一言で

**溜まったインプットと問いから、AI が「別角度の1問」を見出し、問いの棚の先頭に置き、リズムに合わせてプッシュで届ける。**

- 目的: **呼び戻し**（眠っている思考に戻す）
- 手段: **新しい切り口の1問**（既存問いの言い換えではない）
- 置き場: **問いの棚の先頭**（未回答一覧とは別枠）
- 通知: リズム ON 時のみ（静かなトーン）

---

## 2. いまの問いの棚との関係

### 現状（実装済み）

| 要素 | 内容 |
|---|---|
| データ | `open_questions` ビュー = `thread_items` の未回答 `question` |
| UI | `app/(tabs)/shelf.tsx` — 類型フィルタ + 一覧 |
| 性質 | **受動的**（メモ投入 → 分類 → 問い生成で溜まる） |
| AI | 棚画面自体では **AI なし**（閲覧のみ） |

### 本機能が足すもの

| 要素 | 内容 |
|---|---|
| 性質 | **能動的**（スケジュールで1問を「届ける」） |
| 生成 | 過去のメモ・未回答問い・探究を材料に **新1問** |
| 保存 | **勝手に棚に積まない**。「残す」で初めて `thread_items` に入る |
| UI | 棚の **先頭に固定カード**「今日の問い」 |

```
問いの棚（After）
┌─────────────────────────────────────┐
│ 今日の問い                          │  ← NEW（届いているときだけ）
│ 「〜〜？」                          │
│ ↳ ○○のメモに触れて                 │
│     [開く]  [残す]  [あとで]        │
├─────────────────────────────────────┤
│ いま追っている問い N件              │  ← 既存 lead
│ [すべて][深掘り][接続]…            │  ← 既存フィルタ
│ ─ 未回答の問い一覧 ─                │  ← 既存 open_questions
└─────────────────────────────────────┘
```

**棚の意味が「溜まった問い」から「届いた問い + 溜まった問い」に拡張**されるが、自動増殖はしない（T4 原則維持）。

## 2bis. 先頭カードと未回答一覧 — 何が違うのか

問いの棚には **2つのゾーン** がある。同じ「問い」に見えても、**中身の性質が違う**。

### たとえ

| ゾーン | たとえ | 意味 |
|---|---|---|
| **先頭カード「今日の問い」** | **今日届いた手紙** | AI が横断的に見出した提案。**まだあなたの棚（ backlog ）には入っていない** |
| **未回答一覧** | **机の上に積んだ問い** | メモを育てた結果、または **「残す」と決めた問い**。スレッドに存在し、いつでも戻れる |

### データ上の違い

| | 先頭カード | 未回答一覧 |
|---|---|---|
| テーブル | `daily_question_deliveries` | `thread_items`（`open_questions` ビュー） |
| メモとの関係 | **錨**（`anchor_note_id`）で「どのメモに触れているか」示す | **所属**（`note_id`）— そのメモのスレッドの一部 |
| 増え方 | リズムどおり **1日最大1通** | メモ投入・「残す」で増える |
| 消え方 | 残す／あとで／期限切れ | 回答（`answered`）するまで残る |
| フィルタ | カード専用（類型チップはある） | 深掘り・接続…の **既存チップ** の対象 |

### ユーザーにとっての意味

**先頭カードがあるとき**

- 「今日、KOTOI が **1つだけ** 別角度を提案している」
- まだ **追う問いとして登録していない**（義務もない）
- **開く** = 錨メモを見に行くだけ。**残す** = 初めて「追う問い」になる

**未回答一覧に載るとき**

- 「自分の思考の続きとして **ちゃんと置いてある** 問い」
- タップでスレッドへ。追記・調べる・深掘りの起点になる
- メモを放り込んだとき自動で増える問いも、**残した今日の問い**も、**見た目は同じ行**

### なぜ一覧に出さないのか（届け物のうちは）

| もし届けた瞬間から一覧に載せたら… |
|---|
| 毎週1問でも、**見ていない・要らない問い** が backlog を汚す |
| 「棚 = 全部追うべき問い」に見え、**プッシュが義務** に感じる |
| 「残す」の意味が薄れる（既に載っているから） |

**一覧 = 自分が（明示または暗黙に）引き受けた問い**  
**先頭カード = まだ引き受けていない提案**

### 状態遷移（1問の一生）

```
[生成] → 先頭カードのみ
           │
     ┌─────┼─────┬─────────┐
     │     │     │         │
   残す  あとで  開くだけ  翌日（§4.6 案A: expired）
     │     │     │         │
     ▼     ▼     ▼         ▼
  一覧に  消える カード   （検討中）
  載る          残る
  カード
  消える
```

## 3. 既存「呼び戻し」との住み分け

| | ふりかえりの呼び戻し（週次・既存） | 今日の問い（本企画） |
|---|---|---|
| 画面 | ふりかえりタブ | **問いの棚** |
| 中身 | **数週間前の未回答問いを再提示** | **新しい問いを1つ生成** |
| 頻度 | 週1（ふりかえり生成時） | ユーザー選択（既定: 週1） |
| 通知 | `notify_weekly_review` | **新トグル** `notify_daily_question` |
| ねらい | 「まだ生きてる？」 | 「この切り口で戻るとハッとする」 |

**共存する。** 週次ふりかえりで同じ問いが再掲されても、今日の問いは別角度なので衝突しない。

## 4. ユーザー体験（詳細）

### 4.1 初回（設定）

| 段階 | 体験 |
|---|---|
| 1 | 問いの棚を初めて開く（問いが数件以上ある頃が自然） |
| 2 | 棚上部に **一度だけ** 短い説明（チュートリアル層）:「ここに、別角度の問いが届くことがあります」 |
| 3 | 設定 → **「別角度の呼び戻し」** でリズム・通知を選ぶ |

**既定値（前身設計を継承）**

| 設定 | 既定 |
|---|---|
| リズム | 週1 |
| 曜日 | 日曜（ふりかえりと揃えるオプションは後から可） |
| 時刻 | 朝 8:00（**Asia/Tokyo** でサーバ判定。将来ローカル TZ 対応可） |
| 通知 | オン（リズムがオフなら無効） |

### 4.2 届く日（プッシュあり）

| 時刻 | ユーザー | 裏側 |
|---|---|---|
| 8:00 頃 | プッシュ「今日の問いが届きました」 | cron → 生成 Function → DB 保存 → push |
| タップ | **問いの棚**へ（今日の問いカードが見える） | `data.screen = 'shelf'` |
| 開く | 錨のスレッドへ遷移 | `note_id` + 任意 `highlight` |
| 残す | 錨ノートに `thread_items.question` として保存 → **未回答一覧にも載る** | insert + delivery を `saved` に |
| あとで | カードを畳む／非強調。当日中は棚先頭に残す | `dismissed`（再提示クールダウン） |
| **何もしないまま翌日** | **§4.6 案 A** — `active` → `expired`、自動保存なし | — |

### 4.3 届く日（プッシュなし・オフ or 未許可）

- 問いは生成・棚先頭に表示されるだけ
- ユーザーが棚を開いたとき初めて気づく（**静かなデフォルト**）

### 4.4 スキップ日（カードなし）

次のいずれかなら **何も出さない**（「今日はありません」も出さない）:

- リズムがオフ
- 材料不足（後述）
- 直近で「あとで」を連発（クールダウン）
- 当日すでに1問届け済み
- read_only（課金安全弁後）— **要決定**: 生成するか否か

### 4.5 「残す」後

- 通常の未回答問いと同じ行として棚に並ぶ（類型チップ付き）
- 今日の問いカードは消える（または「残しました」→ 消える）
- **出典表示**は既存 `ShelfQuestionRow` と同じ（錨メモのラベル）

### 4.6 意思表明なしで翌日になったとき — **決定: 案 A（消える）**

「見れていない／操作していないものも残す」ニーズは将来 B 等で拡張可能。**MVP は案 A**。

#### 案 A — 消える（**採用**）

| 項目 | 内容 |
|---|---|
| 挙動 | 前日 `active` → `expired`。カード非表示。**`thread_items` には入れない** |
| 翌日 | 新しい今日の問いを届けてよい |
| 実装 | `expireStaleDeliveries`（`ensure` / cron 起動時） |

#### 案 B〜D — 見送り（将来拡張候補）

##### 案 B — 翌日も先頭カードで1日だけ繰り越し

| 項目 | 内容 |
|---|---|
| 挙動 | 翌日も **先頭カード** に「昨日の問い」として表示（見出し or バッジで区別）。2日目の終わりに `expired` |
| 一覧 | **載せない**（届け物のまま） |
| 長所 | 1回見逃しても **もう1チャンス**。自動保存より軽い |
| 短所 | 「今日の問い」が2日連続でカードに。新規配信日と重なると **2枚** になる可能性 → **最大1枚ルール** が要る |
| 実装 | 中（繰り越しロジック + UI ラベル） |

#### 案 C — 未操作なら自動で `thread_items` に残す

| 項目 | 内容 |
|---|---|
| 挙動 | 翌日 0:00 に **自動 insert**（残したのと同じ）。カードは消える |
| 一覧 | **載る** |
| 長所 | 見逃しても backlog に残る |
| 短所 | **意思表明なしに棚が増える**。プッシュが「義務」に感じやすい。「残す」の意味が死ぬ。後から削除の導線が要る |
| 実装 | 中〜大（自動 insert + 通知/説明の設計） |

#### 案 D — 「見逃した問い」専用ゾーン（一覧でもカードでもない）

| 項目 | 内容 |
|---|---|
| 挙動 | `expired` だが別セクション「最近届いた問い（1件）」に **薄く表示**。残す／消すを選べる |
| 長所 | 消えすぎず、一覧も汚さない |
| 短所 | **3ゾーン目** が増え UI が複雑。説明コスト大 |
| 実装 | 大 |

#### 比較サマリ

| 案 | シンプル | 見逃しに強い | 一覧を汚さない | おすすめ度 |
|---|---|---|---|---|
| A 消える | ◎ | △ | ◎ | **MVP 第一候補** |
| B 1日繰り越し | ○ | ○ | ◎ | **第二候補**（見逃し許容したいなら） |
| C 自動保存 | △ | ◎ | × | 非推奨（複雑 + トーン不一致） |
| D 第3ゾーン | × | ○ | ○ | MVP では重い |

#### 判断のための問い（意思決定用）

1. 見逃した問いは **消えてよい** か、**1回くらいは戻してほしい** か？
2. プッシュは **提案** か **積み増し** か？（後者なら C に寄るが、プロダクトトーンと齟齬）
3. 週1ユーザーが **2週連続で見逃した** とき、backlog に2問自動追加（C）は嬉しい？ 邪魔？

**決定**: **案 A 採用**。見逃しが多ければ **B を足す**。C/D は見送り。

### 4.7 設定オフのとき — 棚でオンを促す

`recall_rhythm` の **既定は `off`**。オフのユーザー向けに、問いの棚先頭に誘導カードを出す。

```
┌─────────────────────────────────────┐
│ こんな機能もあります                 │
│ 別角度の呼び戻し                     │
│ 溜まったメモと問いから…             │
│ リズムや時刻は設定で変えられます。   │
│          [スキップ]  [オンにする]    │
│ 設定からいつでも変更できます         │
└─────────────────────────────────────┘
```

| 項目 | 方針 |
|---|---|
| 既定 | **`off`**（新規ユーザー） |
| 表示条件 | `off` かつスキップ未済、かつ今日の届け物なし |
| オンにする | `recall_rhythm = daily` + 選んだ時刻（既定のオン状態） |
| スキップ | 端末ローカルに記録しカード非表示。設定からはいつでもオン可 |
| トーン | 機能の存在を知らせ、押し付けない |

## 4bis. 錨メモの見せ方（UI）

届け物カードでも **どのメモに関する問いか** を必ず見せる（残した後は既存 Row と同じ）。

```
┌ 今日の問い ─────────────────────┐
│ [接続]                          │
│ 「チームの遅さは、決められない  │
│   ことの多さから来ていない？」  │
│                                 │
│ 📄 少人数で速いチームは…        │  ← anchor_note のラベル（既存 formatNoteSourceLabel）
│ ↳ このメモ（と問い）に触れて    │  ← anchor_question があるとき追記
│                                 │
│     [開く]  [残す]  [あとで]    │
└─────────────────────────────────┘
```

| 要素 | データ |
|---|---|
| メモラベル | `notes` join（`raw_text` / `video_title`）— `noteSourceLabel` 再利用 |
| 触れている問い | `anchor_question_id` あり時、1行で抜粋（任意・折りたたみ可） |
| 開く | 常に `anchor_note_id` のスレッドへ |

**残した後**は通常の `open_questions` 行になり、同じ出典ラベルで一覧に並ぶ（二重の世界観にならない）。

## 5. プッシュ設計

### 5.1 文言案

| 項目 | 案 |
|---|---|
| title | `今日の問い` |
| body | 問い本文の先頭 40〜60 字（全文は棚で） |
| data | `{ "screen": "shelf", "delivery_id": "uuid" }` |

トーン: 既存通知（調べる完了・ふりかえり）と同じく **短く、押し付けがましくない**。

### 5.2 技術（既存インフラの拡張）

| 既存 | 拡張 |
|---|---|
| `push_tokens` + `register-push-token` | 変更なし |
| `sendPushToUser` | `settingKey` に `notify_daily_question` 追加 |
| `usePushNotificationNavigation` | `screen === 'shelf'` → `/(tabs)/shelf` + 必要なら `delivery_id` |
| `user_settings` | `recall_rhythm`, `recall_weekday`, `notify_daily_question` 等を追加 |

### 5.3 プッシュしないケース

- 通知 OFF
- トークンなし
- 生成スキップ
- ユーザーがその日すでに棚で「残す」済み（まれ）

## 6. 生成ロジック（企画）

### 6.1 材料（優先順）

| 優先 | 材料 | 理由 |
|---|---|---|
| 1 | 未回答の問い（`open_questions`） | 呼び戻しの主役 |
| 2 | 直近のルートメモ（seed/learn/feeling、14〜30日） | 文脈・温度 |
| 3 | 探究の synthesis / タイトル | 横断の切り口 |
| 除外 | task 主体、feeling の深掘り・反証 | `.cursorrules` 遵守 |

**量の目安**: 未回答 最大5件 + メモ 最大5件 + 探究 最大2件（トークン上限内）。

### 6.2 良い問いの条件（継承）

- **錨必須**: `anchor_note_id`、できれば `anchor_question_id`
- **言い換え禁止**: 既存問いのパラフレーズ NG
- **類型**: `dig|con|ref|act|exp` のいずれか（内容に従う。exp 寄りになりやすい）
- **1問のみ**
- **汎用問い禁止**（プロダクト原則）

### 6.3 AI 出力（JSON）

```json
{
  "anchor": {
    "note_id": "uuid",
    "question_id": "uuid-or-null"
  },
  "question_type": "con",
  "body": "…",
  "why_now": "一言で、この切り口の理由（UIでは小さく）"
}
```

- 軽処理のみ（`generate-questions` より短いプロンプト専用）
- `usage_ledger` 記録・日次上限に含める
- Zod 検証必須

### 6.4 スキップ条件

| 条件 | 例 |
|---|---|
| 材料不足 | 未回答0 かつ 直近メモ0 |
| クールダウン | 直近3回「あとで」でスキップ |
| 重複 | 直近7日以内に同じ `anchor_question_id` で届け済み |
| リズム外 | 平日のみ設定で土日 |

## 7. 問いの「所在」— 既存モデルとの整理（要決定）

### 7.0 いまの正本

KOTOI では **問いの正本は常に `thread_items`（`kind = 'question'`）** で、**必ず1つのルートメモ（`note_id`）のスレッドにぶら下がる**。

```
ルートメモ (notes)
  └── スレッド (thread_items)
        ├── summary（要約）
        ├── question（問い）← 問いの棚 open_questions の元
        ├── user_note / request / result …
        └── parent_item_id で問い→枝の連結も可
```

- **問いの棚** = 全メモ横断の `open_questions` ビュー（未回答 `thread_items` の投影）
- **探究の問い** = `exploration_questions` が既存 `thread_items` を **参照リンク** するだけ（別の問い实体ではない）

つまり「問いはメモに紐づく」は **データ上の不変条件**。今日の問いも最終的にはここに収斂させる。

### 7.1 今日の問いの3段階ライフサイクル（推奨）

今日の問いだけ、一時的に **第2層（届け物）** を持つ。**メモに紐づくのは最初からだが、スレッドにはまだ入れない。**

```
[材料] 複数メモ・未回答問い・探究
         │
         ▼ AI 生成（横断）
[届け物] daily_question_deliveries  ← 新テーブル（正本ではない）
         │ anchor_note_id 必須（主たる錨メモ）
         │ anchor_question_id 任意（触れている既存問い）
         │
    ┌────┴────┐
    │         │
 [開く]    [残す]
    │         │
    ▼         ▼
 錨メモの   thread_items に insert
 スレッドへ   note_id = anchor_note_id
（閲覧のみ） parent_item_id = anchor_question_id（あれば）
             → 以降は普通の問い
    │
 [あとで]
    ▼
 dismissed（届け物だけ消える。スレッドには何も増えない）
```

| 段階 | 所在 | 問いの棚での見え方 |
|---|---|---|
| 届いた直後 | `daily_question_deliveries` | 先頭カード「今日の問い」（**一覧には混ざらない**） |
| 開いただけ | 同上（status は active のまま） | カード残る。スレッド閲覧のみ |
| 残した | `thread_items` + delivery は `saved` | カード消える。**未回答一覧に1行追加** |
| あとで | delivery は `dismissed` | カード消える。スレッド変更なし |

**要点**: 自動では `thread_items` に入れない（棚が勝手に増えない）。**残す = 既存モデルへの昇格**。

### 7.2 錨（anchor）の決め方

生成 JSON の `anchor` は **表示・遷移・保存先のすべて** に使う。

| フィールド | 必須 | 意味 |
|---|---|---|
| `anchor_note_id` | **必須** | 主たるルートメモ。「↳ ○○のメモに触れて」の ○○ |
| `anchor_question_id` | 任意 | 触れている既存の未回答問い。残すとき `parent_item_id` に |

- 材料は横断でも、**保存先スレッドは1メモに限定**（ユーザーが「どの育ちの木に実るか」が分かる）
- 探究だけを錨にする案は **採用しない**（探究の問いは `thread_items` へのリンクであり、問い实体ではない）
- 複数メモにまたがる問いは `why_now` やカード上の補足文で示す（DB 上の第二錨は持たない）

### 7.3 「残す」時の `thread_items` 中身

```ts
// イメージ（Edge で insert）
{
  note_id: delivery.anchor_note_id,
  user_id: delivery.user_id,
  author: 'ai',                    // 既存と同じ
  kind: 'question',
  question_type: delivery.question_type,
  body: delivery.body,
  parent_item_id: delivery.anchor_question_id ?? null,  // 既存問いの枝になる
  answered: false,
  status: 'done',
}
```

- `open_questions` に **そのまま載る**（追加ビュー不要）
- 探究マップへは **自動では載らない**（既存どおりクラスタリング or 手動整理の対象）
- delivery 側 `saved_thread_item_id` で昇格後の行を参照（二重表示防止）

### 7.4 採用しない案

| 案 | 理由 |
|---|---|
| 生成と同時に `thread_items` へ insert | 棚が自動増殖。T4（勝手に増やさない）違反 |
| `note_id` null の問い | `open_questions`・RLS・スレッド UI が全て note 前提 |
| 今日の問い専用ルートメモを自動作成 | 「メモから育つ」体験とズレる。錨が人工的 |
| `exploration_questions` にだけ置く | 問い实体がなく、スレッド・棚と整合しない |
| `thread_items` に `source=daily` 列を足す | 将来あり得るが、MVP では delivery テーブルで足りる |

### 7.5 UI での統一感

| 場所 | 既存の問い | 今日の問い（届け物） | 今日の問い（残した後） |
|---|---|---|---|
| 棚・先頭 | — | 専用カード（見出し「今日の問い」） | — |
| 棚・一覧 | `ShelfQuestionRow` | **出ない**（残すまで） | 同じ Row |
| スレッド | 時系列の question | **出ない**（残すまで） | 同じ question 行 |
| タップ先 | `/note/[id]?itemId=` | `/note/[anchor_note_id]`（任意で item ハイライト） | 同上 |

一覧とカードの **見た目は揃える**（類型チップ・問い本文・出典ラベル）が、**データソースは別** → 残した瞬間に一本化。

### 7.6 エッジケース

| ケース | 扱い |
|---|---|
| 錨メモを削除 | delivery は `anchor_note_id` CASCADE で消える。saved 済みは thread ごと消える |
| 錨の既存問いが answered になった | delivery は残る。`anchor_question_id` は参照のみ（null 化しない） |
| 同日に再生成 | `unique (user_id, delivered_on)` で1日1問 |
| read_only ユーザー | 生成しない（企画どおり） |
| **前日 active のまま翌日** | **§4.6 案 A** — `expireStaleDeliveries` |

### 7.7 決定事項（本節）

| # | 決定 |
|---|---|
| Q1 | 問いの正本は引き続き **`thread_items`（note 紐づけ）** |
| Q2 | 今日の問いは **`daily_question_deliveries` に一時保管** |
| Q3 | **残す** で錨メモの `thread_items` に昇格 |
| Q4 | 錨は **必ず1 `note_id`**。任意で `anchor_question_id` |
| Q5 | 探究は材料・文案のみ。問いの保存先にはしない |

## 8. スケジュール実行（企画）

### 方式候補

| 方式 | 長所 | 短所 | 推奨 |
|---|---|---|---|
| **Supabase pg_cron + Edge** | ユーザー単位で束ねられる | 設定・監視が要る | **MVP 後期** |
| **1時間ごと cron → 対象ユーザーをバッチ** | 8時を JST でまとめやすい | 1時間遅れの可能性 | **MVP 推奨** |
| **アプリ起動時に「届くべきか」判定** | 実装簡単 | プッシュと整合が難しい | プッシュなしなら可 |

**MVP 推奨フロー**

```
毎時 0分 (JST) Edge: schedule-daily-questions
  → recall_rhythm が今日に該当するユーザーを列挙
  → recall_hour が現在時と一致（または過ぎていて未配信）
  → 材料・クールダウン判定
  → generate-daily-question（1ユーザー1回）
  → daily_question_deliveries insert
  → notify_daily_question なら push
```

Supabase Dashboard の **Integrations → Cron**（`pg_cron`）で毎時ジョブを想定。詳細手順は運用時のセットアップメモを参照。

```
0 * * * *  →  schedule-daily-questions（Authorization = DAILY_QUESTION_CRON_AUTH）
```
