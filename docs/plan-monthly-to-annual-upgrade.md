# 月額 → 年額への切り替え導線（企画）

最終更新: 2026-07-21  
前提価格: 月 ¥1,200 / 年 ¥10,000（公開前）  
対象: **一般・月額**（および将来の学割・月額）。年額→月額は本企画のスコープ外。

---

## 1. ねらい

月額で始めた人が、**アプリ内から年額に乗り換えられる**ようにする。

- 年額の方が安い（月換算 ≈¥833）ことを、購読後も思い出せる
- 「解約してから買い直す」を要求しない（ストアのアップグレードに任せる）
- トーンは静か。押し売りではなく **得になる選択肢の提示**

---

## 2. 現状（ギャップ）

| あるもの | ないもの |
|---|---|
| Paywall で月／年を選べる（未購読向け） | 購読中に「年額へ」の明示導線 |
| 設定のプラン表示（月額／年額・次回更新） | 月額ユーザー向けの切り替え CTA |
| RC Webhook が `PRODUCT_CHANGE` を扱い、`plan` を更新しうる | アプリ側の upgrade 専用フロー・コピー |
| 同一 Entitlement `pro` に monthly / annual | ユーザーに見える「差額・いつから」の説明 |

**いま月額の人が年額を買うと**: StoreKit / Play のサブスクリプショングループ内アップグレードとして処理される想定（ASC で **同じサブスクリプショングループ** に両 Product が入っていることが前提）。アプリから `purchasePackage(annual)` を呼べば技術的には近いが、**設定から辿れない・説明がない**のが欠落。

---

## 3. 体験方針（決定案）

### 3.1 入口（必須）

**設定 → プラン**（`trial_state = subscribed` かつ `plan` が `monthly` / `student_monthly` のとき）

```
プラン
月額
次回更新  2026年8月21日

年払いにすると、月あたり約 ¥833（¥10,000 / 年）です。
              [年払いに切り替える]
```

- 年額・学割年額のときは CTA を出さない（または「ご契約中」のみ）
- 解約・請求管理は従来どおり **ストアの購読管理**（リンク or 文言で誘導）。アプリ内で解約 UI は作らない

### 3.2 画面の形（推奨）

新規ユーザー向けフル Paywall をそのまま開かない。

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 設定内で完結（採用）** | プラン欄にヒント＋「年払いに切り替える」。確認 Alert のあと購入 | **実装済み** |
| B. 既存 `/paywall` に `mode=upgrade` | 年額だけ強調、月額カードは隠す | 見送り |
| C. 設定からそのまま `purchasePlan('annual')` | 確認 Alert のみ | 説明不足のため不採用 |

### 3.3 確認で伝えること（必須コピー要素）

Apple / Google の挙動に委ねる旨を短く:

1. **年額の価格**（¥10,000 / 年、月あたり約 ¥833）
2. **いまの月額は、ストアのルールに従って調整される**（日割り・残期間の扱いはストア表示が正）
3. **切り替え後も Pro は途切れない**（同じ `pro`）
4. 失敗・キャンセル時は現状の月額のまま

アプリ側で「あと何円」「いつから年額」を自前計算して断言しない（ストアに任せる）。

### 3.4 任意の弱いリマインド（Phase 2）

- 設定を開いたときだけ、月額ユーザーに薄い1行（毎回モーダルはしない）
- ふりかえりや見取り図完了後のトーストは **見送り**（課金の印象が強すぎる）

MVP は **設定の CTA のみ**でよい。

## 4. ストア／RevenueCat 前提（手作業チェック）

実装前に確認:

| 項目 | 要件 |
|---|---|
| ASC | `kotoi.pro.monthly` と `kotoi.pro.annual` が **同一 Subscription Group** |
| アップグレード | グループ内で年額が上位（またはサービスレベルで upgrade 扱い）になっていること |
| RC | 両 Product が Entitlement `pro`、Offering `default` に載っている |
| Webhook | 既存どおり `PRODUCT_CHANGE` → `subscriptions.plan` / period 更新 |

学割を出す場合も、学割月↔学割年は同じグループ設計が必要。一般↔学割のクロスは本企画では扱わない。

---

## 5. アプリ実装の骨格（メモ・実装時）

1. **表示条件**: `subscribed` && plan ∈ {`monthly`, `student_monthly`}
2. **アクション**: `purchasePlan('annual')`（または student_annual）。RC が既存月額との関係を Store に渡す
3. **成功後**: 既存の `waitForSubscribed` 相当ではなく、`refresh()` で `plan === 'annual'` になるまで短く待つ → 「年払いに切り替えました」
4. **エラー**: 既存 purchase エラー処理。既に年額などの場合は無言 or 短い説明
5. **復元**: 既存「購入を復元」のままでよい

DB 新規テーブルは不要。Webhook の `PRODUCT_CHANGE` が動けば足りる。

---

## 6. やらないこと（MVP）

- 年額 → 月額のダウングレード導線（ストア設定からユーザー自身）
- アプリ内の日割り金額の確定表示
- プッシュ「年払いにしませんか」
- プロモコード専用フロー
- プラン比較の長いマーケティングページ
