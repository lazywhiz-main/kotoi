## 通知機能 — いつ作るか

### すでにできているもの

| 対象 | 状態 |
|------|------|
| 調べる / 深掘り 完了 | ✅ 既存（`notify_agent_done`） |
| ふりかえり 完了 | ✅ 既存（`notify_weekly_review`） |
| **見取り図 完了** | ✅ 今回追加（同じ `notify_agent_done` を流用） |
| プッシュタップで遷移 | ✅ `exploration_id` / `note_id` |
| 設定トグル | ✅ 「調べる・深掘り・見取り図の完了」 |

### まだないもの

| 対象 | いつ作るか |
|------|-----------|
| **探究を更新 完了** | 「探究を更新」のあり方精査 → 非同期化と**同じタイミング**で横転 |
| 通知の細分化（見取り図だけ切る等） | 必要になったら（今は不要） |
| Realtime（プッシュなしでも即反映） | 任意・後回し |

**結論**: 通知の「基盤」はもうある。次に足すのは **探究更新の完了プッシュだけ**で、それは非同期化とセット。単独で先に作る必要はない。

## 次の大きな塊 — 「探究を更新」のあり方精査

**方針変更（合意済み）**:  
非同期化の前に、**「追加されたものをどう消化するか」** の観点で機能そのものを精査する。

### いまの問題（技術以前）

- ボタンは常に押せる（溜まっていなくても）
- 押すと **全探究を作り直し**（ID・見取り図が消える）
- 「更新」が何をするのかユーザーに伝わりにくい
- タイムアウトは症状。根は「毎回フル再クラスタ」という設計

### 精査で決めたいこと（実装前の論点）

| # | 論点 | 例 |
|---|------|-----|
| R1 | **消化の単位** | 未整理の問いだけ足す？ 束を組み直す？ 両方？ |
| R2 | **いつ促すか** | 新問いが n 件溜まったとき／週次／手動のみ |
| R3 | **既存の束との関係** | 既存探究はなるべく維持／大胆に再編可 |
| R4 | **見取り図** | 維持＋stale／作り直し促し／触らない |
| R5 | **操作の名前** | 「探究を更新」以外の方が正しいか（例: 「新しい問いを束ねる」） |

### 進め方

```
1. 精査セッション（設計メモを出す → 論点に OK）
2. 必要ならデータモデル・プロンプト変更
3. そのあとで非同期化（見取り図テンプレ横転）+ 完了プッシュ
```

非同期だけ先にやると、壊れた体験を速くするだけになるので **後回し**。
