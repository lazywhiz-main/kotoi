## 1. なにか

**見取り図**は、ひとつの探究（問いの束）を、人が一目で「この束の空気」を感じられる**一枚の絵**にしたもの。

- 手描きグラレコ／クレヨン画用紙のようなトーンを志向（完璧なインフォグラフィックではない）
- **問いの地図**（構造・ナビ）とは役割が違う。地図が「どこに何があるか」、見取り図が「何の話として残るか」
- 探究のお土産・愛着の対象。だからコストがかかっても、**勝手に消したり描き直したりしない**

コード上の名前は `graphic_rec`（graphic recording）。UI 語彙は必ず **見取り図**。

---

## 2. いつ・誰が作るか

| 項目 | 方針 |
|------|------|
| トリガー | **ユーザーが明示的に生成／更新**（自動一括生成しない） |
| 所要 | おおよそ 2〜3 分（非同期） |
| 待ち | 押した直後に「描いています」系。画面を閉じてもよい |
| 完了 | プッシュ通知（設定のエージェント完了系トグルと共有可） |
| 失敗 | エラー表示＋再試行可能 |

初回チュートリアルでは、探究0の見本カードに見取り図サンプルを載せ「こういうものが付く」と見せる（本物の生成はユーザー操作後）。

---

## 3. ライフサイクルと束の更新

振り分け（増分）で探究の中身が変わったとき:

| 対象 | 扱い |
|------|------|
| synthesis | 静かに新しい文へ（確認不要） |
| 問いの地図 | データに追従して再描画 |
| **見取り図** | **画像は残す**。`graphic_rec_status = stale` |

| 操作 | 見取り図 |
|------|----------|
| 新しい問いを振り分ける | 残す＋stale。促し「見取り図を更新できます」 |
| 見取り図を更新／再生成 | **今の図は消えて描き直し**（事前確認） |
| 束を組み直す | 探究ごと消えるので図も消える（強い確認） |

**原則（R4）**: 中身が変わっても自動では見取り図を作り直さない。

---

## 4. バリアント（絵の切り口）

生成時に AI が選ぶ／理由を残す切り口の例:

| variant | イメージ |
|---------|----------|
| `metaphor` | 比喩・象徴 |
| `narrative` | 物語の一場面 |
| `human` | 人・関係 |
| `spatial` | 空間・配置 |

`graphic_rec_selection_reason` に選定理由を残し、プロンプトはバージョン管理（`graphic_rec_prompt_version`）。

---

## 5. 技術パイプライン（概要）

```
ユーザーが生成
  → explorations.graphic_rec_status = pending（先書き）
  → HTTP 早期 return
  → Edge: Claude で構図・文言 JSON
  → Edge: OpenAI Images で PNG
  → Storage 保存 → status = done（失敗時 error）
  → プッシュ
```

クライアントは詳細・一覧で pending／done／stale／error を表示。  
長押し等で端末へ保存（共有シート）を許容。

---

## 6. UX コピーのトーン

- 待ち: 「2〜3分かかります。終わったらお知らせします。」
- stale: 「見取り図を更新できます」（事務的に長くしない）
- 再生成確認: 「いまの見取り図は消えて、新しく描き直します。」
- 組み直し: 探究と見取り図がすべて作り直される旨を明示

温かく静か。見取り図を「成果物の自慢」にしすぎず、**問いの束の顔**として扱う。

---

## 7. やらないこと（初期）

- 見取り図の自動定期再生成
- サーバ側アーカイブ履歴の本格 UI（必要なら後）
- 見取り図単体の SNS 共有プロダクト化（端末保存で足りる）
- 問いの地図と見取り図の同一キャンバス化（役割を混ぜない）
