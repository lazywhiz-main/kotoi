## 2. 「二重アカウント」とは何か（解像度）

Supabase Auth では、ログインのたびに **どの Identity（提供者＋その提供者上の ID）** で入ったかが付く。

```
auth.users          ← アプリが RLS で見る「1人」
  └─ identities[]   ← apple / google / email など複数あり得る
```

**二重アカウント** = 本来同じ人間なのに `auth.users` が2行できること。  
メモ・問い・探究はすべて `user_id` に紐づくので、**別ユーザーとして空の世界がもう一つできる**。これが「許容しない」の中身。

起きやすいパターン:

| パターン | 何が起きるか |
|----------|----------------|
| P1 | 先にメールOTPで `you@gmail.com` 登録 → 後から Google で同じ Gmail → **うまくいけば同一ユーザー**、設定次第では別ユーザー |
| P2 | 先にメールOTP → 後から Apple（メールを隠す）→ Apple が渡すのは `xxxx@privaterelay.appleid.com` → **メールが一致しないので別ユーザーになりやすい** |
| P3 | 先に Apple（Hide My Email）→ 後から「自分の Gmail」で OTP/パスワード → **別人扱い** |
| P4 | テスターがパスワード用に `a@x.com`、本番感覚で Google の別アドレス → 別ユーザー（運用ミス） |

「メール一致リンク」は主に **P1 を防ぐ仕組み**の話。P2・P3 はメールが一致しないので、**メール一致だけでは防げない**。

## 3. 「メール一致リンク」とは何か

### 3.1 一言

> 新しくログインしようとしている Identity のメールが、既にいるユーザーのメールと同じなら、**新しいユーザーを作らず、既存ユーザーに Identity を足す**。

例（理想の P1）:

1. 既存: `user_id=U1`, email=`you@gmail.com`（OTP で作った）
2. Google で `you@gmail.com` で入る
3. システムが「同じメールだ」と判定 → U1 に `google` identity を追加
4. 次回は Google でも OTP でも **同じメモ空間**

### 3.2 Supabase で実際に触るレバー（概念）

実装時に Dashboard / API で確認する（バージョンで名称が変わるので、実装前に公式ドキュメント再確認）:

- **Automatic linking / 同一メールの自動リンク**  
  有効だと、確認済みメールが一致する Identity を既存ユーザーに結びやすい。
- **手動 linkIdentity**  
  すでにログイン中のセッションに、別プロバイダを後から足す（設定画面の「Google を追加」向き）。
- **メール確認済みかどうか**  
  未確認メール同士の自動リンクは危険なので、通常は「確認済み同士」に限る。

パスワード追加時も同じ: `you@gmail.com` の OTP ユーザーに、後から同じメールでパスワードを設定／リンクできれば二重にならない。

### 3.3 メール一致で「防げる／防げない」

| | メール一致リンクで防げる？ |
|--|--|
| Gmail OTP → 同じ Gmail の Google | ✅ 狙える |
| パスワード `a@x.com` → OTP `a@x.com` | ✅ 狙える |
| Apple Hide My Email → 自分の Gmail | ❌ メールが違う |
| Apple 実メール公開 → 同じメールの Google | ✅ 狙える（ユーザーが「メールを共有」した場合） |

**結論**: 「二重アカウントを許容しない」を本気でやるなら、

1. **確認済みメール一致の自動リンクをオン**（P1 対策の土台）
2. **Apple Hide My Email 問題は別策**が必要（§4）
3. **設定で「今つながっているログイン方法」を見せる**（ユーザーが自分で事故に気づける）

## 4. リスクの解像度（前回挙げたもの＋α）

### R1. Apple の Hide My Email（最重要）

- Apple はユーザーに「メールを隠す」を選べさせる。
- 隠すとアプリ／Supabase に届くのは `…@privaterelay.appleid.com` だけ。
- その人が普段使う Gmail とは **文字列として一致しない**。
- → メール一致リンクでは **同一人物と判定できない**。
- → 先に Gmail で作ったアカウントと、後の Apple ログインが **別 `user_id` になる**典型事故。

**緩和策の選択肢（Q3 で選ぶ）**:

| 策 | 内容 | メリデメ |
|----|------|----------|
| **C1 予防コピー** | ログイン画面で「すでにメールで登録済みなら、同じ方法か、設定から連携してね」と短く書く。Apple では可能ならメール共有を促す（強制はできない） | 実装軽い。事故は減るがゼロではない |
| **C2 ログイン後に連携** | メールで入った人が、設定から「Apple を追加」「Google を追加」（`linkIdentity`） | 正しい一本化手段。Hide My Email でも「既にログイン中の U1 に Apple を足す」なら同一ユーザーを維持できる |
| **C3 手動マージ** | 二重ができてしまったあと、サポートがデータを移す | 運用地獄。初期は作らない |
| **C4 Apple 必須メール** | 使えない（Hide を禁止できない） | — |

**推奨の組み合わせ**: **C1 + C2**。C3 は作らない。  
「許容しない」の実装意味 = **自動で二重を増やさない（リンク設定）＋ユーザーが設定で足せる＋説明**。完全自動で Hide My Email まで吸収はできない、と割り切る。

### R2. 自動リンクの逆リスク（なりすまし）

未確認のメールで「一致したからリンク」すると、他人のアドレスを偽って紐づける攻撃になり得る。  
→ **確認済みメール同士だけ**リンク。OTP／Magic／OAuth の verified を前提にする。

### R3. パスワードと OTP の同居

- 同じメールにパスワードを足すのはテスター向けに便利。
- 「OTP で作ったユーザーに password を set」と「パスワード新規 signUp で別ユーザー」を取り違えると二重になる。
- 実装方針案: **既存メールなら signIn／updateUser でパスワード設定、新規だけ signUp**。画面は「メールで続ける」ウィザードで分岐を明示。

### R4. プロバイダごとの「メアドが取れない／変わる」

- Google は通常安定した email。
- Apple は Hide / 共有で変わる。
- パスワード・OTP はユーザー入力の email がそのまま。

### R5. TestFlight 説明とのズレ

手段が増えると「どう入ればいいか」が迷う。  
→ 「前回ログイン方法」表示（§5）＋ベータ説明の更新がセット。

## 5. 「前回ログイン方法」がわかるようにする

### 5.1 何を覚えるか

端末ローカル（AsyncStorage）に、**この端末で最後に成功した方法**を保存する。

```ts
type LastAuthMethod = 'apple' | 'google' | 'email_otp' | 'email_password';
// kotoi_last_auth_method
```

サーバー必須ではない（個人アプリ・1端末主利用）。  
将来マルチ端末で「アカウントに紐づく主方法」が欲しければ `user_settings` に足せるが、**初期は端末ローカルで十分**。

### 5.2 UI（確定）

ログイン画面（未ログイン時）:

- 前回方法に対応するボタン（Apple / Google / メールOTP / パスワード）の上または角に、小さなバッジ  
  例: **「前回」** または **「前回使った方法」**（短く。ログイン画面のトーンに合わせる）
- バッジ以外の特別なヒーロー文言は必須にしない（ボタン自体で分かるようにする）
- 初回（記録なし）: バッジなし。並びは Apple → Google → メール系

設定（ログイン中）:

- `つながっている方法`: Apple / Google / メール など（Supabase の `user.identities` から表示）
- `この端末の前回ログイン`: ローカルの LastAuthMethod（任意・補助）
- （C2）未連携なら「Apple を追加」「Google を追加」

### 5.3 ログアウト後

前回方法は **消さない**（次に開きやすくするため）。  
「案内をもう一度」とは別。必要なら設定に「前回ログイン表示を消す」は後回しでよい。

## 9. メール OTP とパスワードの共存（UX・合意 2026-07-11）

### 9.1 結論（確定）

| 項目 | 方針 |
|------|------|
| 初回（前回ログインなし） | **確認コード（OTP）をデフォルト** |
| 2回目以降・前回パスワード | **パスワード**＋主ボタン **「メールで続ける」1本** |
| 2回目以降・パスワードなし／忘れた | **OTP を促す**（「忘れた」＝OTP へ。再設定メールは主経路にしない） |
| OTP | チップとして残す（初回・復旧・パスワード未設定） |
| 「新規登録」リンク | **廃止** |
| パスワードの付け方 | ① **初回 OTP 直後の任意オファー** ② **設定から後付け／変更** |
| 役割分担 | OTP＝初回・復旧／パスワード＝慣れた人の近道・テスター |
| ログインUI（2026-07-21） | **B**: 主は確認コード。パスワードは「パスワードで入る」で展開 |

反映済み（ログイン UI・password-offer・前回デフォルト）。

### 9.2 頭の中のモデル

> **同じメールアドレス＝同じ KOTOI の部屋。**  
> 入り方は「確認コード」でも「パスワード」でもよい。どっちで入っても中身は同じ。

| 手段 | 向いているとき |
|------|----------------|
| **確認コード（OTP）** | 初めて／パスワード未設定／忘れた／新しい端末 |
| **パスワード** | 前回パスワードで入った／テスターが手順固定 |

端末ローカルの `lastAuthMethod` でデフォルトを寄せる。新端末・再インストールは「初回」扱いで OTP に戻る（それでよい）。

### 9.3 パスワード動線（整理）

| やりたいこと | どこ |
|--------------|------|
| 毎回入る | ログイン → パスワード →「メールで続ける」 |
| 初めて付ける | **初回 OTP 直後の任意オファー**（下記 S1b） |
| スキップした／あとから付ける・変える | **設定** |
| 忘れた・未設定でパスワード欄に来た | **OTP で入る** → 必要なら設定 |

### 9.4 シナリオ

#### S1. はじめて（OTP）

1. ログイン → メール → **確認コード**（デフォルト）  
2. 送る → コード入力 → 入室  

#### S1b. 初回 OTP 直後のパスワードオファー（任意・1回限り）

入室直後に軽い1枚（設定画面への遷移は不要）:

> パスワードを入れておくと、次回以降パスワードでもログインできます  
> [パスワード] [確認]  
> [設定する]　[あとで]

- **必須にしない**。スキップと設定を同等に扱う  
- **この端末で一度出した／スキップしたら再表示しない**  
- **スキップ時**: 「あとから設定画面でパスワードを設定できます」と短く伝える  
- 設定成功 → 次回デフォルトをパスワード側に寄せられる（`lastAuthMethod`）

#### S2. スキップした人があとから付けたい

**設定 → パスワードを設定**（オファーを出さない人の逃げ道）

#### S3. 毎日パスワードで入る

前回バッジがパスワード → メール＋パスワード →「メールで続ける」

#### S4. パスワードを忘れた／未設定

1. 「パスワードを忘れた」または失敗時案内 → **確認コードで入る**  
2. 入ったあと、必要なら **設定で新パスワード**

#### S5. テスター

主催者が設定（または S1b）でパスワードを付け、メール＋パスワードを渡す。「メールで続ける」だけでよい。

#### S6. OTP のみの人がパスワード欄で失敗

短く案内:「確認コードで入るか、入ったあと設定でパスワードを付けてください。」＋ OTP へ誘導。

#### S7. OTP とパスワードの行き来

同一アカウント。前回バッジだけ切り替わる。

### 9.6 実装メモ（反映済み）

1. 「新規登録」削除。パスワード主ボタンを「メールで続ける」に  
2. 前回なし → `emailMode = otp`。前回 `email_password` → パスワード  
3. 「忘れた」→ 確認コードチップへ誘導（再設定メール主経路は外した）  
4. OTP 検証前に `passwordOfferPending` を立て、`/password-offer` へ  
5. スキップ時「あとで設定画面から…」＋ done フラグ。設定のパスワード設定は残す  
6. 成功時 `lastAuthMethod` を更新

- [x] 初回 OTP デフォルト／2回目以降はパスワード優先／なし・忘れは OTP  
- [x] 初回 OTP 直後の任意パスワードオファー（スキップ可・設定から後付け可と明記）
