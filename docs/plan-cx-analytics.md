# ログ分析・CX計測 — 企画

最終更新: 2026-07-21  
目的: **利用者の体験を良くするための観測**を、プライバシーとプロダクトトーンを壊さずに設計する。  
実装詳細: [`plan-cx-analytics-impl.md`](./plan-cx-analytics-impl.md)（L1 推奨の実装計画）。

---

## 1. ねらいと非ねらい

### ねらい（CX）

「何が起きているか」を数字で見て、次を改善できるようにする。

- コアループがどこで止まるか（放り込む → 問い → 追う → 呼び戻し）
- どの機能が「使われてうれしい」か／放置されているか
- 課金・トライアルのつまずき（Paywall・復元・月→年）
- 障害・失敗体験（失敗したのに気づいていない）

### やらないこと

| やらない | 理由 |
|---|---|
| メモ本文・問い本文・感情メモの内容を分析基盤に送る | 信頼・法務・feeling 方針と衝突 |
| 広告・リターゲティング用トラッキング | Privacy / App Store 申告・トーン不一致 |
| 「エンゲージ最大化」のための押し売り指標だけ追う | 核は問いの質。開封率至上にしない |
| いきなり重い基盤（倉庫＋BI＋10種SDK） | ソロ運用ではメンテ不能 |

## 2. 現状（資産と穴）

| 層 | 現状 | 向いている用途 |
|---|---|---|
| **`usage_ledger`** | AI 呼び出しの fn / tokens / cost | 原価・日次上限・設定の利用内訳 |
| **業務テーブル** | notes / thread_items / daily_question_deliveries / subscriptions 等 | 「何が起きたか」の真実（集計の正本候補） |
| **`lib/analytics.track`** | `__DEV__` の console のみ。本番はほぼ無 | クライアントイベントの差し込み口（SEAM 済み） |
| 実クライアント計測 | SNS 投稿開始など極少数 | ほぼ未整備 |
| クラッシュ | 未導入想定 | 診断ログは別枠 |

**穴**: 「ユーザーが画面で何をしたか／どこで止まったか」の時系列が無い。  
原価は見えるが、**体験ファネルは見えない**。

---

## 3. 設計の三層（混ぜない）

```
① プロダクトイベント（CX）     … 何をしたか・どこで止まったか
② 利用量台帳（usage_ledger）   … AIコスト・上限（既存）
③ 診断（クラッシュ等）         … 壊れているか（将来・任意）
```

- ①と②は **目的が違う**ので表もツールも分けてよい（ダッシュボードで並べるのは可）
- ②を「行動分析」の代わりにしない（コストが上がった＝体験が良い、とは限らない）

## 4. CXで答えたい問い（先に問い、後にログ）

### A. 活性化（コアループ）

1. 初回：アカウント作成 → 最初のメモ → 最初の問い表示、までの到達率と所要時間  
2. 週次：メモを入れた人数 / 問いを開いた人数 / 棚を開いた人数  
3. 「問いを追う」：未回答問いの増減、回答・アーカイブ率  

### B. 差別化機能

4. 今日の問い：オン率、届いた日の開く／残す／あとで比率、スキップ率  
5. 探究・見取り図：生成開始〜完了、失敗、保存／投稿  
6. ふりかえり：作成率、クールダウンで止まった割合  

### C. 収益・継続（押し売りではなく摩擦除去）

7. トライアル → Paywall 表示 → 購入／あとで／離脱  
8. 月額 → 年額 CTA 表示 → 確認 → 成功／キャンセル  
9. 復元の成功率  

### D. 信頼・品質

10. 分類・要約・問い生成の error / タイムアウト  
11. pending が長引いた回数（体験が「止まった」感）  

これらを満たせないイベントは **入れない**（収集のための収集を禁止）。

## 5. イベント設計の原則

1. **名前は動詞＋対象**（例: `note_created`, `shelf_opened`, `daily_question_saved`）  
2. **本文・PII を載せない**。ID・枚举・件数・所要ms・結果コードのみ  
3. **クライアントだけに頼らない**。重要な状態遷移はサーバ（テーブル or Edge）でも分かるようにする  
4. **1ユーザー1日あたりのイベント量に上限意識**（ノイズ・コスト）  
5. **スキーマをバージョン管理**（`event_schema_version` またはドキュメント正本）  

### プロパティの許可リスト（案）

| 許可 | 禁止 |
|---|---|
| `user_id`（自前分析時）／匿名 ID | メール、氏名 |
| `note_id` / `item_id`（UUID） | `raw_text`, 問い本文, transcript |
| `note_type`, `question_type`, `plan` | 感情メモの中身 |
| `screen`, `source`, `result`, `duration_ms` | 精密な位置情報 |
| `error_code`（短い） | スタック全文の無制限送信（診断層は別ポリシー） |

## 6. 最小イベントカタログ（MVP案）

実装は段階的。まず **★** だけ。

### ★ 必須（ファネルの骨格）

| イベント | 発火 | 主な props |
|---|---|---|
| `session_started` | アプリ前面化（間引き可） | `cold_start` |
| `note_created` | メモ保存成功 | `note_type`, `is_video`, `has_url` |
| `thread_opened` | 育つスレッド表示 | `note_id`, `from` |
| `shelf_opened` | 問いの棚フォーカス | `open_count`（任意） |
| `question_opened` | 棚の問い行タップ | `question_type` |
| `daily_question_shown` | 今日の問いカード表示 | `question_type` |
| `daily_question_action` | 開く／残す／あとで | `action` |
| `daily_question_enable` | 誘導でオン／スキップ | `action`, `recall_hour` |
| `paywall_shown` | ペイウォール表示 | `reason` |
| `purchase_result` | 購入結果 | `plan`, `result`（ok/cancel/fail） |
| `annual_upgrade_tapped` | 設定の年額CTA | — |
| `annual_upgrade_result` | 切り替え結果 | `result` |

### ○ 次点

| イベント | 用途 |
|---|---|
| `exploration_opened` / `graphic_rec_result` | 探究CX |
| `review_generated` | ふりかえり |
| `agent_job_result` | 調べる・深掘り完了／失敗 |
| `tutorial_step` | 初回導線 |

### サーバ由来で足りるもの（クライアント不要な場合あり）

- メモ件数・問い件数・delivery の status 分布 → SQL 集計  
- AI 原価 → `usage_ledger`  
- 購読状態 → `subscriptions` + Webhook  

**方針**: 状態は DB、操作の意図・画面到達はイベント。

## 7. 置き場の選択肢

| 案 | 内容 | 向き |
|---|---|---|
| **L1 自前** | `analytics_events`（user_id, name, props jsonb, created_at）+ RLS。Edge or クライアント insert | データ主権・少人数・コスト明瞭 |
| **L2 PostHog 等** | `track()` の差し替え。EU ホスティング検討 | ファネル UI・リテンションがすぐ欲しいとき |
| **L3 ハイブリッド** | 重要イベントは自前、クラッシュは Sentry 等 | 成長期 |

**公開直後〜数十〜数百人**: **L1 または L2 のどちらか1つ**。両方同時は避ける。  
`lib/analytics.ts` の SEAM はどちらの道でも使える。

推奨たたき台:

1. **今〜TF拡大**: L1（Supabase にイベント表）＋ SQL / 簡易ダッシュボード（Metabase は後で）  
2. **ユーザーが増えファネルを毎週見る必要**: L2 に寄せ、ポリシー更新

## 8. ダッシュボード（見るもの）

週1で見る「CXボード」案（最初は SQL ビューで十分）:

1. **Activation**: D1 でメモ≥1、D7 で棚を開いた割合  
2. **問い**: 未回答数の中央値、今日の問いの残す率  
3. **摩擦**: Paywall あとで率、購入 fail、年額キャンセル率  
4. **品質**: agent / graphic error 率（usage や status から）  
5. **原価**: 既存 usage_summary（CXと並べて見るが混同しない）  

個人を名指ししない。必要なら「問題が起きた user_id をサポート用に引く」は別手順。

- [ ] プライバシーポリシーに Analytics 目的を追記（現状は「導入したら Analytics 申告」と明記あり）

広告 SDK・IDFA は使わない前提。

## 10. フェーズ案

| フェーズ | 内容 | 成果 |
|---|---|---|
| **P0 合意** | 本企画の問い・禁止事項・L1/L2 | 方針固定 |

## 11. 成功の定義

- 週次で「コアループのどこが細いか」を **感覚ではなく1枚の集計**で話せる  
- メモ本文が分析基盤に一度も乗っていない  
- ソロがメンテできるイベント数（目安: アクティブ ★ が **20未満**）
