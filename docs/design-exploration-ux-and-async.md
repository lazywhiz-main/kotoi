## A. 「探究を更新」エラーと長時間 Function 戦略

### A.1 いま起きていること（ログの解釈）

```
Http: connection closed before message completed
```

`cluster-explorations` は **HTTP レスポンスを返すまで** 次をすべて同期的に実行している:

1. 全問い・既存探究を集めて Claude へ（`maxTokens: 8192`）
2. **`explorations` を user 単位で全削除**
3. 探究を最大5件まるごと再 insert（notes / questions / subthemes 含む）

見取り図の有無そのものが直接の原因ではないが、

- 探究・問いが増える → Claude の input/output が膨らむ → **処理時間が延びる**
- Supabase Edge Functions の **ウォールクロック上限**（無料枠は短め、Pro でも実質 60〜150 秒帯）を超えると、クライアント側は接続切断エラーになる

`run-research` / `run-deepdive` は既に `EdgeRuntime.waitUntil` で **先に 202 相当の応答 → 裏で完走** のパターン。`cluster-explorations` と `generate-exploration-graphic-rec` は **未対応**。

### A.2 長時間になりうる Function 一覧

| Function | 目安時間 | 現状 | 承認/上限 |
|----------|---------|------|----------|
| `classify-note` パイプライン | 数秒 | 自動・短い | なし |
| `run-research` / `run-deepdive` | 30〜90秒 | **非同期済**（pending item + push） | 承認制 |
| `weekly-review` | 10〜30秒 | 同期 HTTP | 上限チェック |
| `cluster-explorations` | **30〜120秒+** | **同期 HTTP** ← 問題 | 上限チェック |
| `generate-exploration-graphic-rec` | **2〜3分** | 同期 HTTP（DB は pending 先書き） | 上限チェック |

### A.3 推奨パターン（agent と揃える）

**共通ジョブモデル**（`thread_items.status = 'pending'` と同型）:

```
1. クライアントが開始 API を叩く
2. サーバーが即座に { ok, job_id / status: 'pending' } を返す（< 1秒）
3. EdgeRuntime.waitUntil で重処理
4. 完了時: DB 更新 + プッシュ通知（既存 notify_agent_done を流用可）
5. クライアント: ポーリング or Realtime or フォアグラウンド復帰時 refresh
```

探究クラスタ用の追加案:

- `user_settings.cluster_status: idle | pending | done | error`
- または `cluster_jobs` テーブル（将来マルチジョブ向け）

見取り図は **既に `graphic_rec_status: pending` がある** ので、HTTP を早く切るだけで大半は足りる。

### A.4 Refresh トリガー（いつ画面を更新するか）

| 処理 | 待ち UI | 完了の知らせ | Refresh |
|------|---------|-------------|---------|
| 調べる/深掘り | スレッド内 pending カード | プッシュ + 画面フォーカス時 | `useExplorationDetail` 相当を note で |
| 探究を更新 | 探究一覧でバナー「整理中…」 | プッシュ「探究が更新されました」 | 探究タブ focus + 手動 pull |
| 見取り図 | 詳細内プレースホルダ | プッシュ「見取り図ができました」 | 詳細 focus / 10秒ポーリング |
| ふりかえり | ふりかえりタブ spinner | その場 or プッシュ | 生成完了でその画面 |

**原則**: 画面を開きっぱなしで HTTP を待たない。ユーザーは他タブに行ってよい。

### A.5 実装優先度（提案）

1. **P0** `cluster-explorations` を非同期化（エラー解消）
2. **P0** `generate-exploration-graphic-rec` の HTTP を早期 return（pending は既存）
3. **P1** 完了プッシュ（見取り図・探究更新）
4. **P2** Realtime 購読（ポーリング削減）
5. **P3** `weekly-review` の非同期化（必要になったら）

## B. 見取り図 — 待ち UX（コピー案）

トーン: 温かく静か。子供のクレヨン比喩は維持。

### 生成開始直後

> **2〜3分ほどかかります。**  
> 描き終わったらお知らせします。この画面を閉じても大丈夫です。

### 進行中（`graphic_rec_status === 'pending'`、任意で段階表示）

| 経過 | 表示 |
|------|------|
| 0〜30秒 | 構図を考えています… |
| 30秒〜2分 | クレヨンで描いています… |
| 2分〜 | もう少しで仕上がります… |

### 完了（プッシュ本文案）

> **見取り図ができました** — 「{探究タイトル}」を開いて見る

### 失敗

> うまく描けませんでした。もう一度試せます。

ボタンは現状どおり「作り直す」。承認制までは不要（上限内なら即実行でよい）。

## C. 「探究を更新」UX — タイミングと見取り図の運命

### C.1 現状の実装（重要）

`clusterExplorations.ts` は更新のたびに:

```ts
await db.from('explorations').delete().eq('user_id', userId);
// → 新しい UUID で探究を全部作り直す
```

**影響:**

- 探究 **ID がすべて変わる**（ブックマーク・深いリンクが死ぬ）
- **`graphic_rec_*` カラムごと消える**（見取り図メタデータ喪失）
- Storage の PNG は `{user_id}/{旧exploration_id}.png` として **孤児化**

見取り図を作っていたからエラー、というより **成功しても見取り図は消える設計** になっている。

### C.2 更新が「要る」とき / 「要らない」とき

**更新が意味を持つシグナル**

| シグナル | 説明 |
|---------|------|
| 未クラスタの問いがある | どの探究にも入っていない `kind=question` |
| 最後のクラスタ以降にメモが増えた | `notes.created_at > cluster_watermark` |
| 最後のクラスタ以降に問いが増えた | 新規 question items |
| （弱い）回答・追記が増えた | 進行度は DB 更新で足りるが、束の再編成は不要なことも |

**更新が不要なとき**

- 上記いずれもなく、探究一覧を見ただけ
- 既存探究の中で問いに向き合っただけ（**進行度は個別に再計算可能**）

**データ案**（`user_settings` または `users` メタ）:

```text
cluster_watermark_at   — 最後にクラスタが成功した時刻
cluster_snapshot_at    — クラスタ時点の activity watermark（weekly-review と同型）
```

クライアント or 軽量 Edge Function で `needs_cluster = activity_since(cluster_snapshot_at)` を返す。

### C.3 ボタン UI の状態設計

| 状態 | ボタン | 補足コピー |
|------|--------|-----------|
| **最新** | 無効 or テキストリンク程度 | 「探究は最新です」 |
| **少し溜まった**（1〜4 未整理） | 二次ボタン | 「新しい問いが {n} 件あります」 |
| **溜まった**（5+ または初回） | **探究を更新**（現状の強調） | 「似た問いを束ね直します」 |
| **整理中** | スピナー + バナー | 「探究を整理しています…（1〜2分）」 |

探究タブに **バッジ**（未整理あり）を付けると、ボタンを押す動機が自然。

### C.4 見取り図は探究更新後どうするか（推奨方針）

**方針: 「古くなる」として明示し、ID を守る方向に寄せる**

#### 短期（クラスタの delete-all を直すまでの UX）

更新確認ダイアログ:

> 探究の組み替えを行います。  
> **作ってある見取り図は、内容と合わなくなることがあります。**  
> 更新後、必要なら見取り図を作り直してください。

#### 中期（推奨アーキテクチャ）

1. **探究 ID を維持する upsert**  
   - Claude 出力に `existing_exploration_id`（任意）を含める  
   - 同一探究は update、新規のみ insert、消えた探究だけ delete

2. **`graphic_rec_status` に `stale` を追加**  
   - 探究の `question_ids` / `synthesis` が変わったら `stale`  
   - UI: 画像は薄く表示 + 「探究が更新されました。作り直すと反映されます」  
   - 作り直し時のみ再生成（コスト抑制）

3. **変わらなかった探究**  
   - メンバー・synthesis が実質同じ → `graphic_rec` は `done` のまま

4. **Storage**  
   - パスは `{user_id}/{exploration_id}.png` のまま upsert で上書き

#### 長期

- 探究更新後に「見取り図も更新しますか？」を **別承認**（コスト明示）
- 自動再生成はしない（コストと品質）

## D. 探究詳細 — セクションジャンプ案

現状の縦順: **見取り図 → 示唆 → 進行度 → 地図 → 問いリスト**

### 案1: スティッキー・チップナビ（推奨）

画面上部（スクロールで sticky）に横スクロールチップ:

```
見取り図 · 示唆 · 地図 · 問い（12）
```

- タップで `ScrollView.scrollTo`（問いリスト用の `measureLayout` は既存）
- 現在セクションは下線 or 背景色
- 見取り図なしの探究は「見取り図」チップを非表示 or 点線

KOTOI のフラットトーンに合う。実装コスト中。

### 案2: コンパクト「目次」1行

```
このページ: 見取り図 · 示唆 · 地図 · 問い
```

案1の簡易版。初回ユーザー向けに `sectionLead` と併用。

### 案3: アコーディオン

各セクションを折りたたみ可能。地図はデフォルト開、問いは閉じる、など。  
情報量は減るが「何があるか」は見えにくくなる。**優先度低**。

### 案4: 地図を上部固定のヒーローに

見取り図 or 地図をファーストビューに固定し、示唆・問いは下。  
探究の「顔」は地図だが、見取り図追加後は **チップナビの方が公平**。

**推奨**: 案1 + 見取り図があるときはチップ先頭を「見取り図」に。

## E. チュートリアル企画

### 方針

- **コンテキストチュートリアル**（その画面に初めて来たときだけ）が KOTOI に合う
- スキップ常設、二度と出さない
- ゲーミフィケーション・長いスライドショーは避ける
- 語彙は `.cursorrules` 統一（ルートメモ、育つスレッド、問いの棚…）

### 優先度付き一覧

| # | タイミング | 目的 | 形式 | 1〜2文の例 |
|---|-----------|------|------|-----------|
| 1 | 初回 Capture 後 | 放り込むと裏で分類・問いが生まれる | ボトムシート | 「放り込むだけで大丈夫。あとからスレッドが育ちます。」 |
| 2 | 初回メモ詳細 | スレッドの読み方 | コーチマーク3点 | 要約 → 問い（類型色）→ 下に伸びる |
| 3 | 初回 Composer | 4モードの違い | モード切替時ヒント | 「調べる・深掘りは時間がかかります。GO で実行。」 |
| 4 | 初回問いの棚 | 横断の未回答 | 空でなければ1枚 | 「ここは未回答の問いだけ。タップで元スレッドへ。」 |
| 5 | 初回探究一覧 | 束ねる概念 + 更新タイミング | 空状態 or 初回バナー | 「似た問いが束になります。新しい問いが溜まったら更新。」 |
| 6 | 初回探究詳細 | 地図 + チップナビ | 地図上コーチマーク | 「中心が探究。外の点を押すと下の問いへ。」 |
| 7 | 初回見取り図生成 | 時間と通知 | 生成ボタン押下前 | 「2〜3分かかります。終わったらお知らせします。」 |
| 8 | 初回ふりかえり | 週の横断 | カード1枚 | 「今週の流れと、呼び戻しの問いです。」 |
